## What was built, in order

**Round 2 — Managing the floor (HANDOFF-BROWSER-2.md):**

- **Phase 1 — Managing an agent:** In the Command Center header, a manage row `Edit | Note | Pause | Retire | Delete` (red, behind confirm). `Edit` opens a modal pre-filled from `AgentView` (`name`, `role`, `character`, `colour`, `description`, `goal`, `capabilities` comma-separated) and `POST`s to `/api/agents/:id/edit`; `Note` opens a 120-char modal and `POST`s to `/api/agents/:id/note` and appears in the roster’s `note` line. `Pause` toggles `POST /api/agents/:id/pause|resume`, `Retire` → `/retire`, `Delete` behind `confirm()` that counts `Room.memories.filter(m.agentName===a.name).length` and says `This agent's N memories will be kept (server decides). This cannot be undone.` Every call is `postAgent(path,body,errEl)` that shows the server’s own `data.error` (`400`/`404`/`409`) in the row’s `errEl` and keeps draft/focus across `view` broadcasts — no optimistic local copy, per invariant 2. When the server has no endpoint (today: all five return `404`) the UI degrades to `request failed (404)` / `not available yet` and the view does not lie.
- **Phase 2 — Tasks tab + ask-me check:** New `Tasks` tab in the Command Center, `ccRenderTasks` filtering `Room.tasks` where `t.agentId===a.id || t.agentName===a.name`, newest-first, row `title` + `STATE` + `relativeTime`. Empty reads `No tasks for this agent yet…`. Inside the same tab, a small `askBox` (`#fffbf0`/`#f5d99b`) surfaces the existing `ChatMessage.ask` (`chatLog.find(m=>m.ask.taskId===t.id)`) under that task — not a second inbox. Checked `human.ask`/`human.answer` in `apps/server/src/gateway.ts` and `chatLog` in `apps/web/index.html`; the M4 mid-task question flow already exists end-to-end, so `ask-me` is a **re-skin, not new work** — building a parallel inbox would be a bug.
- **Phase 3 — Steer, traces, employee panel:** `Steer` is a single-line `input` + **Steer next task** that `POST`s to `/api/agents/:id/steer` as `{text}` with the note `One line of context for the next task — it lands in the prompt, not in a running process. This is not a terminal.` Draft kept in `window._ccSteerDraft` per `agentId` so a broadcast mid-typing does not reset. `Traces` fetches `GET /api/agents/:id/traces?limit=50` and renders `task.event` `kind`/`summary` as `cmd-row`s; while loading shows `Loading traces…`, on `404` degrades to `Traces not available yet…`, on empty to `No tool calls yet…`. No `xterm.js`, no `contenteditable` — deliberately not a terminal until enrolment (D23). The two-surface split was considered here (`planner` as orchestrator) but not yet split; the recommendation was deferred to Phase 4.

## Phase 4 recommendation and whether it was kept

Recommended **planner as orchestrator** — `AgentRole` already has `planner`, `agents.role` is stored, the `view` already ships it, and the `Add Agent` wizard already lets you pick it. A new `isOrchestrator` boolean would need Stream B to add a column and a way to set it, and the reviewer owns that decision. The alternative — `return all` — restores the single set in one line and is legitimate if the split turns out worse. **Kept the split** — it is better than a single set that shows `triggers` on a `qa` agent and hides `Steer`/`Traces` from the floor. The manage row stays on both surfaces, `Tasks` is on both so no work is stranded, and every pre-existing tab remains reachable. If the reviewer judges it worse, revert `getCCTabs` to `return all`.
