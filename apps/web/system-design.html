How a task crosses the floor

LogBridge agents are one-shot CLI processes, not services. Nothing sits in a loop checking a mailbox. Every mechanism in this document exists to answer one question: given that an agent is not running, how does work reach it — and how do we know it arrived?

inject

A PTY session is already live. A short notice is typed into it. Cheap, and the agent keeps the context it already has.

submitPromptToAgent() · preferred

spawn

No session exists. The CLI is cold-started and the message body becomes its prompt — a fresh process told only "read your inbox" would waste the turn.

spawnAndSubmit() · 10–20 s cold start

MAP

What the system is made of

Four processes and one shared folder. The server is the only thing that holds the whole picture; a runner knows only its own machine's agents; the hive folder is the agents' own shared medium and is the only thing they can see.

The one rule agents follow

An agent never writes into another agent's folder. It drops one JSON file into its own outbox/ and the router delivers it. That single constraint is what makes the floor auditable — every message crosses one place, and that place can refuse it, log it, dedupe it, and retry it.

PHASE 0

Standing the floor up

Before any message exists, each agent has to become three things at once: a database row the office can draw, a folder in the hive it can write to, and a prompt that tells a CLI who it is. All three come from the same place — a role definition file.

What the agent is actually told

The prompt is assembled from three pieces, and the middle one is the role file's own markdown body verbatim. Editing that file changes the prompt, which changes its fingerprint, which makes every live session on that role re-seed by itself — there is no separate invalidation step. 

You are "Sol", the security auditor on this agent floor.

WHAT YOUR ROLE MEANS HERE
## What you do
You audit code for security problems. You report them; you do not patch them.
## Rules
- Every finding needs a file:line and a concrete exploit path.        ← the role file's body

HOW YOU RUN
You are a one-shot process. You were started because there is work for you…    ← commonProtocol()

YOUR FILES (use the env vars, they are already set)
  $AGENT_DIR/memory.md   what you know. Read at start, append at end.
  $AGENT_DIR/inbox/      messages for you. Read every file.
  $AGENT_DIR/outbox/     messages you send. One JSON file per message.
  $HIVE_ROOT/board.md    the shared plan. The commander writes it; everyone reads it.
  $HIVE_ROOT/tasks.json  the shared board. Columns: todo | in_progress | in_review | done

SENDING A MESSAGE
Write ONE JSON file into $AGENT_DIR/outbox/. Never write into another agent's
folder — the router delivers for you.                                  ← floorSection()
Why paths are env vars

An earlier version interpolated 65-character absolute paths eight to fifteen times per prompt while exporting those exact variables and never referring to them. Using $AGENT_DIR is shorter and survives the project folder moving.

PHASE 1

The ask, and the plan

Ayush walks his avatar to Michael and types the goal into the room. Michael is a one-shot process, so "typing at him" means exactly one thing: a write into his live PTY, or a cold start if he has none.

Michael's own prompt draws a line the rest of the floor depends on — small requests get dispatched, not planned. A one-line question does not trigger a PRD. This one is a real project, so he takes the long path.

One dispatch file, as written

// hive/agents/agt_michael/outbox/2026-08-31T09-14-02-ada.json
{
  "to": "agt_ada",
  "act": "request",
  "subject": "Implement the OAuth callback route",
  "body": "OBJECTIVE: add GET /auth/callback exchanging code for a session\nOUTPUT: apps/server/src/routes/auth.ts, migration for sessions table\nSPECS: reuse existing session cookie shape; no new deps\nREFERENCES: read $HIVE_ROOT/board.md",
  "say": "Ada — callback route is yours, specs are on the board.",
  "requires_reply": true
}
Two audiences, one file

body is what the recipient acts on. say is what humans read in the office chat — the personality is part of the product. say is never authoritative, so a loosely worded sentence can only ever produce a confusing line, never a wrong action. Same split as a commit message and its diff. If an agent omits say, the server generates a line rather than posting nothing; a silent office is the exact failure this design exists to prevent.

PHASE 2

Dispatch: what the router does to each file

Every 1500 ms the router scans every hive root it knows about, walks agents/*/outbox/*.json, and puts each file through the same gauntlet. The file is deleted whether it succeeded or failed — the durable record lives in the database, not the folder.

Sole scribe: the refusal path

Sol, mid-audit, decides the finding belongs on the shared board and writes a message targeting board.md. Only the commander may write those four files. The router does not silently drop it — it manufactures a reply and puts it in Sol's inbox, which is the only way a one-shot process will ever learn it was refused. 

// delivered to hive/agents/agt_sol/inbox/refusal-….json
{
  "from": "agt_michael",  "to": "agt_sol",  "act": "refuse",
  "in_reply_to": "msg-1756…",
  "subject": "Write to board.md refused",
  "body": "Sole scribe violation: \"agt_sol\" cannot write \"board.md\" directly.
            Only god (agt_michael) is authorized. Message god with your
            proposed change so god can update it."
}

The refusal tells Sol what to do instead, so the next turn is productive rather than a repeat. It also fires the same onMessageCallback as any other delivery — meaning Sol gets woken to read it.

PHASE 3

Waking: turning a file into a running process

This is the heart of the system. A message is not something an agent receives — a message is a reason to run an agent. The order of the checks below is not arbitrary.

Why "starting" is its own status

A booting CLI used to report idle — the same value a ready agent reports. For the whole 10–20 second cold start a booting agent was indistinguishable from one ignoring you, and nothing on screen said "wait".

Four agents wake at once

Michael's four dispatch files are all picked up on the same tick. Noor and Ada are local and idle with no live terminal, so both are spawned. Sol has a terminal open because Ayush was reading it, so Sol is injected. Kite is on Sam's laptop.

PHASE 4

Across machines: offers, consent, and sealing

Kite and Rhen live on Sam's laptop. Nothing on Ayush's machine can start a process there — it can only ask. Two different mechanisms carry that ask, and they exist for different reasons.

A. Task offers — the server assigns work

When a task exists in the database with no agent, the orchestrator scores every candidate and picks one. Capability match is worth 40 points and is also a hard gate: an agent missing the task's required_capability is disqualified outright, not merely ranked lower.

If Sam closes his laptop

Heartbeats stop, the lease expires, and the sweep fails the task with "machine went offline — lease expired". The failure is classified, and if the retry policy allows it a new task is created — preferring a different agent, so the work moves to Ayush's machine rather than waiting for Sam to wake up.

Agents whose CLI runs as an in-process PTY on the server's own machine cannot send heartbeats at all, so they are given a deliberately long lease. Otherwise the sweep would fail a task out from under a terminal that was still visibly working on it.

B. Sealed delegation — an agent asks to borrow a machine

Different situation: Ada wants Rhen to review her diff, and the request carries content that should not sit in cleartext on the server in between. This is the path with real cryptography and a human gate.

PHASE 5

Reporting back, and the board

Every agent finishes the same way its prompt tells it to: append what it learned to memory.md, move the handled message into inbox/.done/, and write a reply into its own outbox. That reply travels back through the identical router path — there is no separate "reply" channel.

Verification is the commander's job

Michael's prompt tells him to check the files a subordinate claims to have written against what he asked for. "Done" on its own is not a report — every employee prompt says so explicitly, and asks for file paths, commands, and real output instead.

PHASE 6

When a message does not land

Kite's laptop went to sleep between the router delivering the message and the wake attempt. The message file is already in Kite's inbox — the folder is shared — but nothing is running to read it, and nothing will be until Sam opens the lid. This is what the delivery ledger is for.

A bug this design has already survived

The duplicate check originally ran unconditionally, and isAlreadyDelivered returns true the moment any row exists — which recordDelivery inserts on the very first attempt regardless of outcome. So every retry hit "duplicate" and did nothing. Attempts still climbed, the sweep still "tried" three times, and every message whose first wake failed was guaranteed to dead-letter, with the middle two attempts pure theatre. The retry path now passes skipDedup; the router path still does not.

Where state actually lives

Three stores, and knowing which one owns what explains most of the system's behaviour under failure.

StoreOwnsSurvivesVisible to agents
SQLite
data.db		 agents, tasks, events, deliveries, grants, sessions, memories everything except a deleted file no — only through their prompt

project folder		 board.md, tasks.json, registry.json, inboxes, outboxes, memory.md, identity.md server restarts; it is just files yes — this is their entire world

Why the split is not accidental

Agents can only be given a filesystem. They are CLIs — no database driver, no API token, no socket. So everything they must read or write is a file, and everything the office must guarantee (delivery, dedup, retries, leases) is in SQLite where a crash cannot lose it. The router is the translation layer between those two facts.

REF

What the prompt promises that the code does not

Two things every agent is told about have no enforcement behind them today. They are listed here because a diagram that hides them would be a nicer picture and a worse map.

The circuit breaker is prompt-only

Every employee prompt ends with: "A circuit breaker watches the floor. If you receive 'Circuit breaker: steer/constrain' you are looping or overspending…" Nothing in the server or the runner ever sends that string. Per-task budgets (maxSeconds, maxUsd) are enforced by the runner's harness, and a human can steer an agent by hand — but there is no watcher detecting a loop and intervening.

The supervisor is manual

evaluateWorkflowHealth() and executeSupervisorAction() can pause, resume, cancel, and reassign — but they are only reachable through HTTP routes a human calls. No loop invokes them. Automatic recovery today is exactly one thing: the lease sweep retrying work whose machine went offline.

Both are the same shape of gap — the mechanism exists, the trigger does not. Closing either is a loop and a threshold, not a redesign.
